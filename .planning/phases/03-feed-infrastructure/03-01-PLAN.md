<task type="auto">
  <name>Task 2: Refactor DeribitClient for bidirectional WS communication with heartbeat protocol</name>
  <files>src/feed/deribit/client.rs</files>
  <action>
Refactor `DeribitClient::start()` to support bidirectional WebSocket communication. Currently the write half sends the subscribe request then is only used for close frames. After this task, the spawned task owns both read and write halves and handles heartbeat protocol inline.

**Changes to the spawned task in `start()`:**

1. **Move write half into the spawned task.** The subscribe request should still be sent before spawning (it's part of connection setup). But after spawning, the write half moves into the task for heartbeat responses.

2. **Send `public/set_heartbeat` after subscribe.** Before entering the read loop, send:
```json
{"jsonrpc":"2.0","id":<N>,"method":"public/set_heartbeat","params":{"interval":10}}
```
The interval comes from `config.heartbeat_interval_ms / 1000` (convert ms to seconds). Minimum 10 per Deribit docs.

3. **Add heartbeat timeout timer.** Create a `tokio::time::interval` or `sleep` that resets on every received message (any message, not just heartbeats). If no message arrives within `heartbeat_interval_ms * 2` (2x the heartbeat interval), the connection is dead. On timeout, log a warning and break out of the read loop (the supervisor in Plan 03 will handle reconnection; for now, the read loop just exits).

   Implementation approach: Use `tokio::time::Instant` to track `last_message_at`. In the select loop, add a `tokio::time::sleep_until(last_message_at + timeout_duration)` branch. When it fires, check if `last_message_at` is still old -- if so, connection is dead.

4. **Handle heartbeat messages in the read loop.** When a text message is received:
   - Parse for heartbeat: check if the raw text contains `"method":"heartbeat"` (fast string check) or parse via DeribitMessage and match the Heartbeat variant.
   - If it's a heartbeat with `type: "test_request"`, respond immediately with:
     ```json
     {"jsonrpc":"2.0","id":<N>,"method":"public/test","params":{}}
     ```
     Send this response WITHOUT going through a rate limiter (per research pitfall 6: heartbeat responses must be prompt, exempt from rate limiting).
   - If it's a regular heartbeat (`type: "heartbeat"`), just update `last_message_at` and continue.
   - If it's NOT a heartbeat, forward to the raw message channel as before and update `last_message_at`.

5. **Do NOT forward heartbeat messages to the raw_tx channel.** Heartbeats are connection-level protocol messages, not market data. The processor does not need them.

6. **Return value change:** The `start()` method signature stays the same (`-> anyhow::Result<mpsc::Receiver<RawMessage>>`). The heartbeat handling is internal to the client.

**Key constraints:**
- The REQUEST_ID atomic counter is already global static -- use it for heartbeat request IDs.
- The `write` half must be moved into the spawned task (not shared via Arc/Mutex -- single owner is simpler and correct since only the spawned task writes after setup).
- Keep the existing `CancellationToken` shutdown path -- cancel still sends Close frame and exits.
