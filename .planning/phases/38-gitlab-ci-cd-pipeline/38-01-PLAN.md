  <name>Task 1: Refactor Dockerfile with cargo-chef dependency caching</name>
  <files>Dockerfile</files>
  <action>
Refactor the existing 2-stage Dockerfile into a 3-stage cargo-chef build:

**Stage 1: Planner** (FROM rust:1.85 AS planner)
- `cargo install cargo-chef`
- WORKDIR /build
- COPY Cargo.toml Cargo.lock and src/
- `cargo chef prepare --recipe-path recipe.json`

**Stage 2: Builder** (FROM rust:1.85 AS builder)
- `cargo install cargo-chef`
- `apt-get update && apt-get install -y libssl-dev pkg-config` (same as current)
- WORKDIR /build
- COPY --from=planner /build/recipe.json recipe.json
- ENV CARGO_BUILD_JOBS=2 (keep existing constraint)
- `cargo chef cook --release --recipe-path recipe.json` (this layer cached when deps unchanged)
- COPY Cargo.toml Cargo.lock and src/
- `cargo build --release`

**Stage 3: Runtime** (FROM debian:bookworm-slim) -- keep identical to current:
- Install ca-certificates, libssl3, curl
- COPY prediction, spread-analytics, signal-scoring binaries
- EXPOSE 9000 9001
- CMD ["./prediction", "--config-dir", "config"]

Pin rust image to 1.85 (matches rust-version in Cargo.toml). Do NOT use rust:latest.

The key optimization: the `cargo chef cook` layer only rebuilds when Cargo.toml or Cargo.lock change. Source-only changes skip the entire dependency compilation.
  </action>

<task type="auto">
  <name>Task 2: Create .gitlab-ci.yml with test, build-and-push, and deploy stages</name>
  <files>.gitlab-ci.yml</files>
  <action>
Create `.gitlab-ci.yml` in project root with 3 stages:

**Global variables:**
```yaml
variables:
  ECR_REGISTRY: "606103597377.dkr.ecr.us-east-1.amazonaws.com"
  ECR_REPOSITORY: "prediction"
  AWS_DEFAULT_REGION: "us-east-1"
```

**Stage 1: test**
- image: rust:1.85
- Set CARGO_HOME to ${CI_PROJECT_DIR}/.cargo for cache locality
- Cache key: `cargo-${CI_COMMIT_REF_SLUG}` with paths `.cargo/registry/`, `.cargo/git/`, `target/`
- Script: `cargo test --release`
- Rules: only on master branch (`if: $CI_COMMIT_BRANCH == "master"`)

**Stage 2: build-and-push**
- image: docker:27
- services: docker:27-dind
- DOCKER_TLS_CERTDIR: "/certs"
- before_script: install aws-cli via `apk add --no-cache aws-cli`, then ECR login via `aws ecr get-login-password | docker login`
- Script: `docker build` with two tags (commit SHA and latest), then push both
- Rules: only on master branch

**Stage 3: deploy**
- image: amazon/aws-cli:2 (NOT apk-installed awscli -- guaranteed v2 with ssm wait support)
- Script:
  1. Run `aws ssm send-command` targeting `${EC2_INSTANCE_ID}` with document AWS-RunShellScript
  2. Commands to send: `systemctl stop prediction`, `cd /opt/prediction && /opt/prediction/fetch-secrets.sh`, `docker compose pull`, `systemctl start prediction`, `sleep 25`, `for i in 1 2 3 4 5; do curl -sf http://localhost:9001/health && exit 0; sleep 5; done; echo HEALTH CHECK FAILED && exit 1`
  3. Capture CommandId from output (--query "Command.CommandId" --output text)
  4. Run `aws ssm wait command-executed --command-id "$CMD_ID" --instance-id "$EC2_INSTANCE_ID"` to block until complete
  5. Fetch command output with `aws ssm get-command-invocation --command-id "$CMD_ID" --instance-id "$EC2_INSTANCE_ID"` and print stdout/stderr for debugging
  6. Check invocation status -- if not "Success", exit 1
- Rules: only on master branch
- timeout: 10 minutes (generous for SSM wait)

**Important details:**
- All three CI variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, EC2_INSTANCE_ID) come from GitLab Settings > CI/CD > Variables -- do NOT hardcode them
- Use `$CI_COMMIT_SHA` for image tag (exact traceability)
- The deploy health check uses a retry loop (5 attempts, 5s apart) after the initial 25s sleep to handle startup jitter
- The `fetch-secrets.sh` call in SSM command refreshes ECR auth token and .env file before pull
  </action>
  <verify>Validate YAML syntax: `python3 -c "import yaml; yaml.safe_load(open('.gitlab-ci.yml'))"` or equivalent. Verify the file contains all 3 stages, correct image references, and no hardcoded AWS credentials.</verify>
  <done>.gitlab-ci.yml exists with test (cargo test), build-and-push (docker build + ECR push), and deploy (SSM send-command + health verify) stages. All stages gated to master branch. No hardcoded secrets.</done>

  <action>
Add an IAM user with minimal permissions for CI/CD pipeline operations to the CDK stack. Add these resources after the existing IAM section:

**IAM User:** `CiDeployUser`
- Create an IAM user named `prediction-ci-deploy`
- This user's access keys will be configured as GitLab CI variables

**IAM Policy:** Inline policy with two statements:
1. **ECRPush** -- Allow pushing images:
   - Actions: `ecr:GetAuthorizationToken` (Resource: "*" -- required by AWS)
   - Actions on ECR repo ARN: `ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage`
2. **SSMDeploy** -- Allow sending commands to EC2:
   - Actions: `ssm:SendCommand` (Resource: instance ARN + `AWS-RunShellScript` document ARN)
   - Actions: `ssm:GetCommandInvocation`, `ssm:ListCommandInvocations` (Resource: "*")

Use `iam.User`, `iam.PolicyStatement`, and `iam.Policy` CDK constructs. Reference the existing `ecrRepo` and `instance` variables for ARN scoping.

For the SSM document ARN, construct it as: `arn:aws:ssm:${region}::document/AWS-RunShellScript` (note: account-less ARN for AWS-owned documents).

Add a CfnOutput for the IAM user name so the operator knows which user to create access keys for:
```typescript
new cdk.CfnOutput(this, 'CiDeployUserName', {
  value: ciDeployUser.userName,
  description: 'IAM user for GitLab CI/CD pipeline -- create access keys in IAM console',
});
```

Do NOT create access keys in CDK (they'd appear in CloudFormation outputs in plaintext). The operator creates them manually in IAM console.

Import `iam` if not already imported (it likely is already).
