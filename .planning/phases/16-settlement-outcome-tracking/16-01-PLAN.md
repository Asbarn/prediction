**traits.rs:** Define the `ResolutionChecker` async trait:
```rust

pub trait ResolutionChecker: Send + Sync {
    async fn check_resolution(

        event_id: &str,
        venue_instrument: &str,
    ) -> anyhow::Result<ResolutionResult>;
    fn venue(&self) -> Venue;
}
```
Note: The project does not use async_trait crate. Use the standard Rust approach -- since Rust 1.75+ supports `async fn` in traits directly via `impl Future` return types, but given the `dyn` dispatch requirement, use the `async_trait` pattern. Check if `async-trait` is in Cargo.toml. If not, use manual `Pin<Box<dyn Future>>` approach or add `async-trait` crate. Actually -- check existing codebase patterns first. If no async trait exists, use a synchronous-compatible design where `check_resolution` returns `Pin<Box<dyn Future<Output = Result<ResolutionResult>> + Send + '_>>`. Alternatively, since the SettlementMonitor will own concrete checker types (not `dyn`), make the trait non-object-safe with plain `async fn` and use an enum dispatch pattern instead. **Prefer the enum dispatch approach** to avoid new crate dependencies: create `VenueChecker` enum wrapping the three concrete types, with a `check_resolution` async method that delegates.

Implement the three venue-specific resolution checkers, each as a struct implementing the check_resolution pattern via the VenueChecker enum dispatch from Task 1.

**deribit.rs -- DeribitResolutionChecker:**
- Fields: `client: reqwest::Client`, `base_url: String`, `rate_limiter: Arc<governor::RateLimiter<...>>` (match existing `VenueRateLimiter` type from `feed::reliability::rate_limiter`).
- Constructor: `new(client, base_url, rate_limiter)`.
- Internal response structs (private, Deserialize only): `DeribitDeliveryResponse { result: DeribitDeliveryResult }`, `DeribitDeliveryResult { data: Vec<DeribitDeliveryEntry> }`, `DeribitDeliveryEntry { date: String, delivery_price: f64 }`.
- `check_resolution` method: Takes `event_id`, `venue_instrument` (unused for Deribit -- we need expiry, strike, direction from EventMapping context). **Design decision:** The method signature takes `event_id` and `venue_instrument`, but Deribit needs the expiry date, strike, and direction. The TrackedEvent already carries these. Pass them via a separate context or extend the trait. **Approach:** Add a `CheckContext` struct to traits.rs containing `expiry: String`, `asset: String`, `strike: Decimal`, `direction: Direction`. The VenueChecker dispatch method takes `CheckContext` alongside the existing params.
- Implementation: Derive `index_name` from `asset` (lowercase + "_usd", e.g., "btc_usd"). Query `{base_url}/api/v2/public/get_delivery_prices?index_name={index_name}&count=30`. Rate limit via `rate_limiter.until_ready().await`. Parse response. Find entry where `entry.date` matches `context.expiry`. If found, convert `delivery_price` to Decimal via `Decimal::from_f64_retain`, compare against strike: if delivery >= strike and direction is Above -> Yes, else No (and vice versa for Below). Return `Resolved { outcome, settlement_price: Some(delivery), resolved_at: Utc::now() }`. If no matching date found, return `NotYetResolved`.
- **PITFALL:** Deribit delivery price is keyed by index_name, NOT by instrument name. Match by expiry date.
- Log at debug level the raw delivery price and computed outcome.

**kalshi.rs -- KalshiResolutionChecker:**
- Fields: `client: reqwest::Client`, `rest_url: String`, `api_key_id: String`, `private_key: rsa::RsaPrivateKey`, `rate_limiter: Arc<...>`.
- Constructor: `new(client, rest_url, api_key_id, private_key, rate_limiter)`.
- Internal response structs: `KalshiMarketResponse { market: KalshiMarketDetail }`, `KalshiMarketDetail { ticker: String, status: String, result: Option<String>, settlement_value_dollars: Option<String>, settlement_ts: Option<String> }`.
- `check_resolution` method: Rate limit. Sign request using `feed::kalshi::auth::sign_kalshi_request(&self.private_key, timestamp_ms, "GET", &path)`. The path is `/trade-api/v2/markets/{ticker}` where ticker is `venue_instrument`. Send GET with headers KALSHI-ACCESS-KEY, KALSHI-ACCESS-SIGNATURE, KALSHI-ACCESS-TIMESTAMP. Parse response.
- Status dispatch: "determined" | "finalized" -> check result field. "yes" -> Resolved(Yes), "no" -> Resolved(No), "scalar" -> Ambiguous (Kalshi Rule 6.3(c)). "disputed" -> Disputed. Others -> NotYetResolved.
- Parse `settlement_value_dollars` for settlement_price. Parse `settlement_ts` for resolved_at (falling back to Utc::now()).
- **PITFALL:** Check for `status` in `["determined", "finalized"]` and verify `result` is non-empty.
- **PITFALL:** Kalshi Rule 6.3(c) -- when `result == "scalar"` or `settlement_value_dollars` is fractional (not 0 or 1), treat as Ambiguous.

**polymarket.rs -- PolymarketResolutionChecker:**
- Fields: `client: reqwest::Client`, `gamma_api_url: String`, `price_lock_threshold: f64`, `rate_limiter: Arc<...>`.
- Constructor: `new(client, gamma_api_url, price_lock_threshold, rate_limiter)`.
- Internal response struct: `GammaMarketResponse { condition_id: String, active: bool, closed: bool, outcome_prices: Option<String>, uma_resolution_statuses: Option<String> }`. Use `#[serde(rename = "conditionId")]` etc. per research.
- `check_resolution` method: Rate limit. Query `{gamma_api_url}/markets?id={condition_id}` where condition_id is `venue_instrument`. Parse response as `Vec<GammaMarketResponse>` (API returns array). Take first element.
- Two-stage check: (1) If `!closed` -> NotYetResolved. (2) Parse `outcome_prices` JSON string (it's a JSON string inside JSON: `"[\"0.95\", \"0.05\"]"`). If yes_price >= threshold AND no_price <= (1 - threshold) -> Resolved(Yes). If no_price >= threshold AND yes_price <= (1 - threshold) -> Resolved(No). Check `uma_resolution_statuses` for "disputed"/"DVM" -> Disputed. Else if closed but prices not locked -> NotYetResolved (keep polling).
- **PITFALL:** `outcomePrices` is a JSON string inside the JSON response, not a native JSON array. Must parse twice: first as String from serde, then deserialize the string content.
- **PITFALL:** No explicit "resolved" field exists. Two-stage check is authoritative.
- Log `raw_response` on every resolution detection (include full JSON for paper trading validation).

**Update traits.rs:** Add `CheckContext` struct. Update VenueChecker enum to wrap all three. Implement async `check_resolution(&self, event_id: &str, venue_instrument: &str, context: &CheckContext) -> Result<ResolutionResult>` on VenueChecker, dispatching to the concrete type.
