Create `src/settlement/monitor.rs` implementing the SettlementMonitor following the AlertMonitor pattern from Phase 14.

**SettlementMonitor struct fields:**
- `registry: Arc<RwLock<EventRegistry>>` -- read access for event lookup and expiry awareness
- `checkers: HashMap<Venue, VenueChecker>` -- venue-specific resolution checkers keyed by venue
- `tracked_events: HashMap<String, Vec<TrackedEvent>>` -- active polling targets, keyed by event_id (multiple venues per event)
- `settlement_tx: mpsc::Sender<SettlementOutcome>` -- output channel to PaperTradeTracker
- `liveness: Arc<PipelineLiveness>` -- record settlement check timestamps
- `config: SettlementConfig` -- polling configuration
- `cancel: CancellationToken` -- graceful shutdown

**Constructor: `SettlementMonitor::new(...)`**
Accept all fields. The constructor does NOT populate `tracked_events` -- that happens via `initialize_from_registry()` and `enqueue_backfill()`.

**`pub async fn run(mut self)` method:**
Follow AlertMonitor pattern exactly:
```rust
let mut interval = tokio::time::interval(
    Duration::from_secs(self.config.base_poll_interval_secs)
);
interval.tick().await; // skip first immediate tick

loop {
    tokio::select! {
        biased;
        _ = self.cancel.cancelled() => {
            tracing::info!(tracked = self.tracked_events.len(), "SettlementMonitor shutting down");
            break;
        }
        _ = interval.tick() => {
            self.poll_cycle().await;
            self.liveness.record_settlement_check();
        }
    }
}
```

**`async fn poll_cycle(&mut self)` method:**
Core polling loop. For each tracked event with active polling tier:

1. Check if the polling tier should advance (call `tier.advance(config)` from types.rs). Update tier in tracked_events.

2. Determine if this event should be polled this cycle. Each TrackedEvent has a `last_checked` timestamp. Compare elapsed time against `tier.interval(config)`. If not enough time has passed, skip. This allows the base_poll_interval to be fast (e.g., 60s) while individual events poll at their tier-appropriate cadence.

3. For events due for polling:
   - Build `CheckContext` from TrackedEvent fields (expiry, asset, strike, direction).
   - Look up the `VenueChecker` for this event's venue.
   - Call `checker.check_resolution(event_id, venue_instrument, &context).await`.
   - Handle result:
     - `NotYetResolved` -> update `last_checked`, continue.
     - `Resolved { outcome, settlement_price, resolved_at }` -> Build `SettlementOutcome` from result. Send via `settlement_tx.send(outcome).await`. Transition tier to `Resolved`. Log at INFO level with full context. Emit `metrics::counter!("settlement_outcomes_total", "venue" => ..., "outcome" => ...).increment(1)`.
     - `Disputed { dispute_started }` -> If currently Aggressive, transition to Patient. Log at WARN level. Keep polling.
     - `Ambiguous { raw_data }` -> Build `SettlementOutcome` with `OutcomeKind::Ambiguous`. Send on channel. Transition to Resolved. Log at WARN level with raw_data.
   - On error from check_resolution: log at WARN, do NOT transition tier, will retry next interval.

4. For events transitioning to `TimedOut`: Build `SettlementOutcome` with `OutcomeKind::Timeout`. Send on channel. Remove from tracked_events. Log at WARN level. Emit timeout counter metric.

5. Clean up: Remove fully resolved events from `tracked_events` (both legs resolved or timed out).

**`pub fn initialize_from_registry(&mut self, open_positions: &[PaperPosition])` method:**
Called during startup. For each open position:
- Look up the event_id in the EventRegistry to get EventMapping.
- For each venue in the EventMapping.venues (deribit, polymarket, kalshi): if a checker exists for that venue AND that venue has an instrument mapping, create a TrackedEvent with:
  - `polling_tier: PollingTier::Waiting` (will be promoted by trigger logic)
  - `venue_instrument` from the EventMapping.venues
  - `expiry`, `asset`, `strike`, `direction` from EventMapping
- Check the trigger condition: For Deribit, if current time is past 08:00 UTC on expiry date, start in Aggressive tier. For prediction markets, start in Aggressive if paired Deribit event is already resolved OR if event is past its expiry date. Otherwise Waiting.

**`pub fn enqueue_backfill(&mut self, open_positions: &[PaperPosition], checkpoint_timestamp_ms: i64)` method:**
Called during startup recovery. For each open position:
- Check `last_settlement_check` timestamp from the position (if available, otherwise use checkpoint_timestamp_ms).
- If elapsed time since last check > max_lookback_days * 86400 * 1000 (ms): Mark as `resolution_timeout` immediately -- build SettlementOutcome with Timeout, but don't send here (caller will send after). Actually, store in a `backfill_timeouts: Vec<SettlementOutcome>` field for the caller to drain.
- Otherwise: Create TrackedEvent entries with appropriate tier (skip Waiting, start in Aggressive if past expiry, Patient if within patience window).
- Sort backfill events oldest-first.

**Trigger logic for Deribit:**
In poll_cycle, for events in `Waiting` tier with a Deribit venue:
- Parse expiry date from TrackedEvent.expiry as NaiveDate.
- If today (UTC) >= expiry date AND current_hour >= 8 -> Transition to Aggressive.

**Trigger logic for prediction markets (Polymarket, Kalshi):**
- If paired Deribit event in same event_id has transitioned to Resolved -> Transition prediction market events to Aggressive (lazy-then-aggressive anchor).
- If no paired Deribit event AND current date >= expiry date -> Transition to Aggressive with moderate initial cadence.

**Rate limiting for backfill:**
During poll_cycle, if a TrackedEvent was created via backfill (add a `is_backfill: bool` field to TrackedEvent), use `rate_limiter.try_acquire()` style check (non-blocking). If rate limit denied, skip to next tick. This ensures live feeds take priority during startup contention.
