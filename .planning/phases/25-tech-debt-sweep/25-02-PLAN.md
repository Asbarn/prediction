<objective>
Fix Kalshi staleness computation to use exchange_timestamp instead of always returning false (FIX-03).

Purpose: Kalshi `is_stale` has been hardcoded to `false` since v1.0, meaning stale Kalshi data bypasses the SpreadEngine staleness gate. This can produce phantom spread signals from stale prediction market prices paired with live options data. The exchange timestamp and staleness threshold are already available in the processor -- they just are not wired together.

Output: Kalshi normalizer computes `is_stale` from exchange timestamp age, mirroring the pattern used by Polymarket and Deribit normalizers.
</objective>

  <name>Task 1: Compute Kalshi is_stale from exchange_timestamp (FIX-03)</name>
  <files>src/feed/kalshi/normalize.rs</files>
  <action>
    **Step 1: Replace the hardcoded `is_stale = false` (~line 272)**

    The `exchange_ts_ms: Option<i64>` variable is already computed at lines 255-270 from `self.last_exchange_ts`. The `self.staleness_threshold_ms` field already exists on `KalshiProcessor`.

    Replace:
    ```rust
    let is_stale = false;
    ```

    With:
    ```rust
    let is_stale = exchange_ts_ms
        .map(|ts| {
            let now_ms = chrono::Utc::now().timestamp_millis();
            let age_ms = (now_ms - ts).max(0) as u64;
            age_ms > self.staleness_threshold_ms
        })
        .unwrap_or(false);
    ```

    This mirrors the Polymarket normalizer pattern at polymarket/normalize.rs:134-139. When `exchange_ts_ms` is `None` (no timestamp available yet), `is_stale` defaults to `false` (same as before), which is correct since we cannot determine staleness without a timestamp.

    **Step 2: Add a tracing warn log for stale data (after the is_stale computation)**

    Add after the `is_stale` computation, before the latency metrics block:
    ```rust
    if is_stale {
        tracing::warn!(
            market = %market_ticker,
            age_ms = exchange_ts_ms.map(|ts| (chrono::Utc::now().timestamp_millis() - ts).max(0) as u64).unwrap_or(0),
            threshold_ms = self.staleness_threshold_ms,
            "Kalshi exchange data stale"
        );
    }
    ```

    **Expected behavior change:** Once this fix is applied, `SpreadEngine.passes_staleness_gate()` (spread/engine.rs:424) will correctly reject stale Kalshi data. Previously, stale Kalshi snapshots were always accepted. This is desired behavior -- it prevents phantom spreads from stale data.

    The staleness threshold is configurable in venues.toml `[kalshi] staleness_threshold_ms` (default 5000ms). Operators can adjust if Kalshi data latency is higher than expected.
