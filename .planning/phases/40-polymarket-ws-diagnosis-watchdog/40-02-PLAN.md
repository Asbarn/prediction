Modify `PolymarketSupervisor::run()` to wrap the `raw_rx.recv()` call with `tokio::time::timeout` to detect silent freezes.

**Add imports:**
- `use std::time::Duration;` (already imported, verify)
- No new crate imports needed -- `tokio::time::timeout` is in the `tokio` crate already used.

**In the forwarding loop** (the inner `loop` after successful connection), replace the `msg = raw_rx.recv()` select arm with:

```rust
result = tokio::time::timeout(
    Duration::from_secs(self.config.data_timeout_secs),
    raw_rx.recv()
) => {
    match result {
        Ok(Some(raw)) => {
            if !received_first {
                received_first = true;
                backoff.reset();
                self.health.mark_available();
                tracing::info!(
                    "PolymarketSupervisor: first message received, backoff reset"
                );
            }
            if tx.send(raw).await.is_err() {
                tracing::warn!(
                    "PolymarketSupervisor: downstream receiver dropped, exiting"
                );
                return;
            }
        }
        Ok(None) => {
            self.health.mark_unavailable("connection lost".to_string());
            tracing::warn!(
                attempt = attempt,
                "PolymarketSupervisor: connection lost, will reconnect"
            );
            break;
        }
        Err(_elapsed) => {
            self.health.mark_unavailable("data inactivity timeout".to_string());
            metrics::counter!(
                "feed_data_timeout_total",
                "venue" => "polymarket"
            ).increment(1);
            tracing::warn!(
                timeout_secs = self.config.data_timeout_secs,
                "PolymarketSupervisor: data inactivity detected, forcing reconnect"
            );
            break; // -> reconnect with backoff (do NOT reset backoff)
        }
    }
}
```

**Critical design decisions (from research):**
1. The timeout wraps only `raw_rx.recv()`, NOT the entire `select!` -- cancellation and subscription-change arms remain responsive.
2. The timeout resets automatically each loop iteration (each call to `timeout()` starts a fresh timer).
3. On timeout, break to the reconnect loop WITHOUT resetting backoff -- this is a failure, not intentional reconnect. If the server keeps silently freezing, backoff grows appropriately.
4. `raw_rx` only carries text frames (PING/PONG filtered by client internally), so the timeout correctly measures data inactivity, not connection liveness.

**Do NOT:**
- Add a separate watchdog task or timer
- Reset backoff on timeout (only reset on first message after reconnect, existing behavior)
- Add application-level heartbeat (Polymarket has none, and PING/PONG works during freezes)
