**src/paper_trade/tracker.rs:** The paper trade tracking engine:

- `pub struct PaperTradeTracker`:
  - `pending: Vec<PaperPosition>` (signals awaiting next-tick fill)
  - `open: Vec<PaperPosition>` (active positions being tracked)
  - `config: PaperTradeConfig` (notional_per_trade, log_mtm, log_dir)
  - `aggregator: DailyAggregator`
  - `trade_logger: BufWriter<File>` (JSONL for individual trade events)

- `pub struct PaperTradeConfig`: `notional_per_trade: Decimal`, `log_mtm: bool`, `log_dir: String`
  - Derive `Debug, Clone, Deserialize, Serialize` with defaults

- `PaperTradeTracker::new(config: PaperTradeConfig) -> Self`

- `pub async fn run(mut self, mut signal_rx: mpsc::Receiver<SpreadResult>, mut snapshot_rx: mpsc::Receiver<MarketSnapshot>, cancel: CancellationToken)`:
  Main loop using `tokio::select!` with biased selection:
  1. `cancel.cancelled()` -> log final summary, break
  2. `daily_tick.tick()` -> emit daily rollup for yesterday (check if day boundary crossed)
  3. `signal_rx.recv()` -> create PaperPosition::new_pending, add to pending list
  4. `snapshot_rx.recv()` -> process snapshot:
     a. Check pending positions: if this snapshot matches a pending position's event_id and venue, fill it (next-tick entry). Compute fill prices from the snapshot (use walk-the-book on the new snapshot's depth). Move to open list. Log entry.
     b. Update MTM on open positions: for each open position matching this event_id, compute current spread from latest snapshots and call update_mtm(). Log MTM if config.log_mtm is true.

- **Next-tick fill logic** (per user decision: "Entry: fill at next tick after signal fires"):
  When a MarketSnapshot arrives for an instrument involved in a pending position:
  1. Determine which venue this snapshot is from
  2. Walk the book on the relevant depth side for this venue's role in the pattern
  3. If both sides have been filled (or this is the matching venue), transition to Open
  4. The key insight: the signal fires on snapshot N, the entry happens on snapshot N+1 for the same instruments. The pending position stores which event_id and pattern it needs, and fills on the NEXT matching snapshot.

- **Settlement**: For v1, positions are settled when the event expires (from EventRegistry lifecycle status). The settlement P&L is computed as the actual outcome minus entry cost. For now, positions that reach expiry without settlement data are marked as "unsettled" in the log. Settlement tracking is logged but not blocking.

- Metrics:

  - `metrics::gauge!("paper_trades_open").set(self.open.len() as f64)` on each change
  - `metrics::histogram!("paper_trade_pnl", "event" => event_id).record(pnl_f64)` on settlement
  - `metrics::gauge!("paper_trade_daily_pnl").set(today_pnl_f64)` on daily rollup
