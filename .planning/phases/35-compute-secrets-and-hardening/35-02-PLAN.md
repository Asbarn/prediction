Deploy the updated CDK stack with the new user-data and Secrets Manager template:

1. Run `cd infra/cdk && npx cdk diff` to preview changes. Expect to see:
   - Updated UserData (additional commands for Docker, systemd, fetch-secrets, CW agent)
   - Updated Secret template (key name changes from DERIBIT_CLIENT_ID to DERIBIT_API_KEY etc.)
   - No other resource changes

2. Run `npx cdk deploy --require-approval broadening` to deploy.

3. After deploy, the EC2 instance will need to be replaced or have its user-data re-executed because user-data only runs on first boot. Since the existing instance already ran its original user-data, the updated user-data will NOT automatically apply.

**To apply the new user-data**, the instance must be stopped and started (or terminated and recreated by CDK). The simplest approach:
- Option A: Terminate the existing instance, let CDK recreate it on next deploy. This requires adding a comment or changing a property that forces instance replacement (e.g., changing the instance description or adding a tag).
- Option B: Use SSM to manually run the user-data commands on the existing instance.

**Recommended: Option A** -- since this is pre-production and the EBS data volume has `deleteOnTermination: false`, terminating the instance is safe. Add a small change to force replacement (like a metadata comment), or simply terminate the instance via AWS console/CLI before `cdk deploy`.

If Option A: Run `aws ec2 terminate-instances --instance-ids i-0aad98de6b901811c --region us-east-1` before `cdk deploy` so CDK creates a fresh instance with the new user-data.

4. After deploy completes, get the new instance ID from stack outputs.

5. Wait 2-3 minutes for user-data to complete, then verify via SSM:
```bash
aws ssm start-session --target <new-instance-id> --region us-east-1
```

  </what-built>
  <how-to-verify>
**Prerequisites:** Populate Secrets Manager with real credentials (at minimum DERIBIT_API_KEY and DERIBIT_API_SECRET):
```bash
aws secretsmanager put-secret-value --secret-id prediction/prod/credentials --region us-east-1 \
  --secret-string '{"DERIBIT_API_KEY":"your-key","DERIBIT_API_SECRET":"your-secret","POLYMARKET_PRIVATE_KEY":"","KALSHI_API_KEY_ID":"","KALSHI_PRIVATE_KEY":""}'
```

Also copy config files to `/opt/prediction/data/config/` via SSM Session Manager.

**Verification steps (via SSM Session Manager):**

1. **Check fetch-secrets works:**
   ```bash
   sudo /opt/prediction/fetch-secrets.sh
   sudo cat /opt/prediction/.env  # Should show key=value pairs (not PLACEHOLDER)
   ```

2. **Check systemd service status:**
   ```bash
   sudo systemctl restart prediction
   sudo systemctl status prediction  # Should show active (running)
   ```

3. **Check container is running:**
   ```bash
   cd /opt/prediction && sudo docker compose ps  # Should show prediction container Up
   curl -f http://localhost:9001/health  # Should return 200
   ```

4. **Test graceful shutdown (HARD-03):**
   ```bash
   CONTAINER_ID=$(sudo docker compose -f /opt/prediction/docker-compose.yml ps -q prediction)
   sudo docker stop --time 30 $CONTAINER_ID
   sudo docker inspect $CONTAINER_ID --format='{{.State.ExitCode}}'  # Should be 0, NOT 137
   sudo docker logs $CONTAINER_ID 2>&1 | tail -20  # Should show shutdown messages
   ```

5. **Test auto-restart after reboot (HARD-02):**
   ```bash
   sudo reboot
   # Wait 2-3 minutes, reconnect via SSM
   sudo systemctl status prediction  # Should be active
   sudo docker compose -f /opt/prediction/docker-compose.yml ps  # Container running
   ```

6. **Check CloudWatch agent:**
   ```bash
   sudo systemctl status amazon-cloudwatch-agent  # Should be active
   ```
   Then check AWS CloudWatch console -> Metrics -> Custom Namespaces -> Prediction/EC2 for CPU/memory/disk metrics.

**Expected outcomes:**
- fetch-secrets.sh writes .env with real credentials
- systemd starts docker-compose, container is healthy
- SIGTERM produces exit code 0 (graceful shutdown)
- Reboot auto-starts the service
- CloudWatch agent reports host metrics
