# Phase 35: Compute, Secrets, and Hardening - Research

**Researched:** 2026-03-07
**Domain:** EC2 user-data bootstrap, AWS Secrets Manager, systemd, Docker graceful shutdown
**Confidence:** HIGH

## Summary

Phase 35 bridges the gap between the CDK-provisioned infrastructure (Phase 34) and a running application. Three distinct concerns must be addressed: (1) EC2 user-data that bootstraps a fresh Amazon Linux 2023 instance with Docker, the CloudWatch agent, and a systemd service; (2) a `fetch-secrets.sh` script that retrieves venue API credentials from Secrets Manager and exports them as environment variables before docker-compose starts; (3) graceful SIGTERM handling inside the container so checkpoints are flushed and WebSocket connections are closed cleanly.

The existing codebase already handles SIGTERM correctly via `shutdown.rs` (listening for both SIGINT and SIGTERM via `tokio::signal::unix::signal(SignalKind::terminate())`), and the `PaperTradeTracker::run()` method already flushes checkpoints, trade logs, and settlement logs on cancellation. The main work is therefore infrastructure scripting (user-data, systemd unit, fetch-secrets) and Docker configuration (`stop_grace_period`, signal propagation).

A critical discovery is a **key name mismatch** between the Secrets Manager secret (which uses `DERIBIT_CLIENT_ID`, `DERIBIT_CLIENT_SECRET`, `DERIVE_WALLET_KEY`) and the environment variables the Rust code reads (`DERIBIT_API_KEY`, `DERIBIT_API_SECRET`, `POLYMARKET_PRIVATE_KEY` plus `KALSHI_API_KEY_ID`, `KALSHI_PRIVATE_KEY`). The `fetch-secrets.sh` script must either remap these, or the Secrets Manager secret template must be updated to match the Rust code's expectations. The cleaner approach is to update the CDK secret template to use the exact env var names the Rust code expects.

**Primary recommendation:** Update the CDK Secrets Manager template to match the Rust code's env var names, extend user-data with Docker/CW agent install plus systemd unit, create fetch-secrets.sh, and add `stop_grace_period: 30s` to docker-compose.yml.

### Pattern 2: Systemd Unit File

**What:** A systemd service that runs fetch-secrets.sh then docker-compose up.
**When to use:** Boot-time auto-start and crash recovery.

```ini
[Unit]
Description=Prediction Market Arbitrage System
After=docker.service network-online.target
Requires=docker.service
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/prediction
ExecStartPre=/opt/prediction/fetch-secrets.sh
ExecStart=/usr/bin/docker compose up --no-build
ExecStop=/usr/bin/docker compose down
Restart=on-failure
RestartSec=10
TimeoutStopSec=45

# Environment
Environment=AWS_DEFAULT_REGION=us-east-1

[Install]
WantedBy=multi-user.target
```

Key details:
- `ExecStartPre` runs `fetch-secrets.sh` before compose starts
- `Restart=on-failure` handles crashes but not manual stops
- `RestartSec=10` prevents restart storms
- `TimeoutStopSec=45` gives Docker's `stop_grace_period` (30s) time to complete plus buffer

### Pattern 3: Secrets Fetch Script

**What:** Shell script that reads from Secrets Manager and writes a `.env` file for docker-compose.
**When to use:** Before every docker-compose start (via ExecStartPre).

```bash
#!/bin/bash
set -euo pipefail

REGION="us-east-1"
SECRET_NAME="prediction/prod/credentials"
ENV_FILE="/opt/prediction/.env"

# Fetch secret JSON
SECRET_JSON=$(aws secretsmanager get-secret-value \
  --region "$REGION" \
  --secret-id "$SECRET_NAME" \
  --query SecretString \
  --output text)

# Write .env file (docker-compose reads this automatically)
{
  echo "DERIBIT_API_KEY=$(echo "$SECRET_JSON" | jq -r '.DERIBIT_API_KEY')"
  echo "DERIBIT_API_SECRET=$(echo "$SECRET_JSON" | jq -r '.DERIBIT_API_SECRET')"
  echo "POLYMARKET_PRIVATE_KEY=$(echo "$SECRET_JSON" | jq -r '.POLYMARKET_PRIVATE_KEY // empty')"
  echo "KALSHI_API_KEY_ID=$(echo "$SECRET_JSON" | jq -r '.KALSHI_API_KEY_ID // empty')"
  echo "KALSHI_PRIVATE_KEY=$(echo "$SECRET_JSON" | jq -r '.KALSHI_PRIVATE_KEY // empty')"
} > "$ENV_FILE"

chmod 600 "$ENV_FILE"
echo "Secrets fetched and written to $ENV_FILE"
```

### Pattern 4: Docker stop_grace_period

**What:** Configure Docker to wait before sending SIGKILL after SIGTERM.
**When to use:** docker-compose.yml for graceful shutdown.

```yaml
services:
  prediction:
    # ... existing config ...
    stop_grace_period: 30s
```

The Rust application's shutdown sequence on SIGTERM:
1. `shutdown_signal()` catches SIGTERM, cancels `CancellationToken`
2. All spawned tasks check `cancel.cancelled()` with biased select (highest priority)
3. WS clients send Close frame to Deribit/Derive/Polymarket
4. `PaperTradeTracker` emits final daily summary, flushes trade/settlement loggers, writes final checkpoint
5. Main `shutdown_token.cancelled().await` resolves, `tracing` guard drops (flushes logs)
6. Process exits with code 0

Default Docker stop timeout is 10 seconds, which may be too short. 30 seconds gives ample time.

### Anti-Patterns to Avoid

- **Hardcoding secrets in user-data:** Never put credentials in EC2 user-data or AMI. Always fetch at runtime from Secrets Manager.
- **Using `docker-compose` v1 (Python):** AL2023 does not ship it. Use `docker compose` v2 (Go binary plugin).
- **Running fetch-secrets.sh as a one-time init:** Secrets should be re-fetched on every service restart to pick up rotations. Use `ExecStartPre` not a one-time user-data step.
- **Using `Restart=always` in systemd:** `on-failure` is correct; `always` would restart after manual `systemctl stop` which is confusing during maintenance.
- **Forgetting `--no-build` in docker compose up:** The EC2 instance has no Rust toolchain; images must be pre-built and pulled from ECR.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Service management | Custom daemon/cron scripts | systemd unit | Handles boot ordering, restart, logging, stop signals |
| Secrets retrieval | Custom HTTP calls to SM API | AWS CLI + jq | Handles auth, retries, IAM role assumption automatically |
| Docker registry auth | Manual token management | `aws ecr get-login-password` | Handles STS token exchange, credential caching |
| Host metrics collection | Custom scripts pushing to CW | amazon-cloudwatch-agent | Handles CPU/memory/disk with zero custom code |
| Signal propagation to container | Custom PID 1 / tini | Docker's built-in init (or exec form CMD) | Dockerfile already uses exec form `CMD ["./prediction", ...]` |

**Key insight:** This phase is 95% infrastructure scripting with well-established AWS patterns. The Rust application already handles signals correctly; the task is ensuring the infrastructure delivers SIGTERM properly and gives enough time for cleanup.

## Common Pitfalls

### Pitfall 1: Secrets Manager Key Name Mismatch

**What goes wrong:** The CDK secret template uses `DERIBIT_CLIENT_ID` / `DERIBIT_CLIENT_SECRET` / `DERIVE_WALLET_KEY` but the Rust code reads `DERIBIT_API_KEY` / `DERIBIT_API_SECRET` / `POLYMARKET_PRIVATE_KEY` (plus Kalshi keys not in the template at all).
**Why it happens:** The CDK template was created as a placeholder shell before the Rust credential loading code was reviewed.
**How to avoid:** Update the CDK Secrets Manager template to use the exact env var names from `src/config/credentials.rs`: `DERIBIT_API_KEY`, `DERIBIT_API_SECRET`, `POLYMARKET_PRIVATE_KEY`, `KALSHI_API_KEY_ID`, `KALSHI_PRIVATE_KEY`. Then re-deploy with `cdk deploy`.
**Warning signs:** Container starts but all credentials show as `None` in logs.

### Pitfall 2: Docker Compose .env File Not Read

**What goes wrong:** docker-compose doesn't pick up the `.env` file generated by fetch-secrets.sh.
**Why it happens:** The `.env` file must be in the same directory as `docker-compose.yml`, or explicitly referenced with `env_file:` in the compose file.
**How to avoid:** Ensure `fetch-secrets.sh` writes to `/opt/prediction/.env` and `docker-compose.yml` is also in `/opt/prediction/`. Add `env_file: .env` explicitly in docker-compose.yml for clarity.
**Warning signs:** `docker compose config` shows empty environment variables.

### Pitfall 3: Docker Compose Sends SIGTERM to Wrong Process

**What goes wrong:** SIGTERM goes to a shell wrapper instead of the Rust binary, so the app gets SIGKILL after timeout.
**Why it happens:** Using shell form `CMD` in Dockerfile (e.g., `CMD ./prediction`) runs via `/bin/sh -c` which doesn't forward signals.
**How to avoid:** The existing Dockerfile already uses exec form: `CMD ["./prediction", "--config-dir", "config"]`. This is correct. Do not change it.
**Warning signs:** Container exits with code 137 (SIGKILL) instead of 0.

### Pitfall 4: EBS Volume Not Mounted Before Docker Starts

**What goes wrong:** docker-compose starts before the EBS data volume is mounted, so volume mounts point to the root filesystem.
**Why it happens:** systemd service starts before user-data completes, or fstab entry is wrong.
**How to avoid:** The user-data (Phase 34) handles mount and fstab. The systemd unit's `After=` dependency on `docker.service` plus `cloud-final.service` ensures user-data completes first. Alternatively, the mount should be in fstab (already done) which systemd processes before `multi-user.target`.
**Warning signs:** Data files appear on root volume instead of /opt/prediction/data.

### Pitfall 5: ECR Login Token Expires

**What goes wrong:** `docker compose pull` fails with auth errors after 12 hours.
**Why it happens:** ECR tokens expire after 12 hours.
**How to avoid:** Run `aws ecr get-login-password | docker login` in `ExecStartPre` or in `fetch-secrets.sh` before every `docker compose up`. This ensures fresh credentials on every restart.
**Warning signs:** `docker compose pull` returns 401 Unauthorized.

### Pitfall 6: CloudWatch Agent Missing Config

**What goes wrong:** amazon-cloudwatch-agent installs but doesn't collect metrics.
**Why it happens:** The agent requires a JSON config file specifying which metrics to collect.
**How to avoid:** Create `/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json` with CPU, memory, and disk metrics configuration. Start with `amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s -c file:/path/to/config.json`.
**Warning signs:** No EC2 host metrics in CloudWatch despite agent being installed.

## Open Questions

1. **Docker Compose file deployment mechanism**
   - What we know: The docker-compose.yml needs to be on the EC2 instance at `/opt/prediction/`
   - What's unclear: Should it be baked into user-data (heredoc), pulled from S3, or deployed via CI/CD?
   - Recommendation: For Phase 35, embed in user-data or write via `cat <<'EOF'`. CI/CD (Phase 38) will handle updates later. Keep it simple now.

2. **Config files deployment**
   - What we know: The app reads config from `/app/config` (mapped to host `/opt/prediction/data/config/`)
   - What's unclear: How do config.toml, events.toml, venues.toml get onto the instance initially?
   - Recommendation: For Phase 35, include a note that config files must be manually placed or deployed via CI/CD. This is a Phase 38 concern.

3. **Secrets Manager secret update (key name fix)**
   - What we know: Current CDK template has wrong key names
   - What's unclear: Whether the user has already manually populated the secret with real credentials
   - Recommendation: Update the CDK template and re-deploy. If secret already has real values, the user will need to re-populate after deploy since `generateSecretString` will reset it. Alternative: update keys in AWS console manually without CDK redeploy.
