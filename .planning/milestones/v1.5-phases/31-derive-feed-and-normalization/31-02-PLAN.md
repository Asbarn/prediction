  <files>src/pricing/instrument.rs</files>
  <action>
    Add `parse_derive_instrument()` function alongside the existing `parse_deribit_instrument()` in `src/pricing/instrument.rs`.

    **Function signature:** `pub fn parse_derive_instrument(name: &str) -> Option<ParsedInstrument>`

    **Implementation:**
    1. Split name by '-' -- must have exactly 4 parts
    2. parts[0] = asset (e.g., "BTC")
    3. parts[1] = date string in YYYYMMDD format (exactly 8 chars, all digits)
       - Parse using `NaiveDate::parse_from_str(date_str, "%Y%m%d")`
       - This naturally REJECTS Deribit's DDMMMYY format because "27JUN25" is not 8 digits
    4. parts[2] = strike price (parse as f64)
    5. parts[3] = "C" or "P" -> OptionType::Call or OptionType::Put

    Return `ParsedInstrument { asset, expiry, strike, option_type }` (same struct as Deribit parser).

    **Add unit tests (critical cross-format rejection):**
    - Parse valid Derive call: `BTC-20260305-69500-C` -> correct ParsedInstrument
    - Parse valid Derive put: `BTC-20260627-100000-P` -> correct ParsedInstrument
    - Derive parser REJECTS Deribit format: `parse_derive_instrument("BTC-27JUN25-100000-C")` returns None
    - Deribit parser REJECTS Derive format: `parse_deribit_instrument("BTC-20260305-69500-P")` returns None
    - Parse malformed inputs: empty string, too few parts, invalid date, invalid strike, invalid option type all return None
    - Parse single-digit strike: `BTC-20260305-500-P` works correctly
    - Date validation: `BTC-20261301-69500-C` (month 13) returns None
  </action>
  <verify>

  </verify>
