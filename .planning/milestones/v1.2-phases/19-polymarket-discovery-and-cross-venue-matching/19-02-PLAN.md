**Add FuzzyMatchKey type (in src/events/discovery.rs):**

1. Add `FuzzyMatchKey` struct with `#[derive(Debug, Clone, Hash, Eq, PartialEq)]`: fields `asset: String`, `strike: Decimal`, `direction: Direction`. This is the three-field key (no expiry) for tolerance-based matching.

2. Implement `FuzzyMatchKey::from_discovered(d: &DiscoveredInstrument) -> Self` that uppercases asset, copies strike and direction.

**Add find_cross_venue_candidates_fuzzy function:**

3. Implement `pub fn find_cross_venue_candidates_fuzzy(instruments: &[DiscoveredInstrument], expiry_tolerance_days: i64) -> Vec<(FuzzyMatchKey, Vec<&DiscoveredInstrument>, ExpiryConfidence)>`:
   - Pass 1: Group all instruments by `FuzzyMatchKey` into a `HashMap<FuzzyMatchKey, Vec<&DiscoveredInstrument>>`.
   - Pass 2: For each group, check that 2+ different venues are present (`HashSet<Venue>` from instrument venues). Skip groups with < 2 venues.
   - Pass 2 continued: Compute expiry spread (max - min of all `inst.expiry` dates using `NaiveDate` arithmetic). Skip groups where spread exceeds `expiry_tolerance_days`.
   - Compute `ExpiryConfidence` via `compute_expiry_confidence` on the expiry dates.
   - Collect results as `Vec<(FuzzyMatchKey, Vec<&DiscoveredInstrument>, ExpiryConfidence)>`.

**Add filter_new_candidates_fuzzy function:**

4. Add `pub fn filter_new_candidates_fuzzy(candidates: &[(FuzzyMatchKey, Vec<&DiscoveredInstrument>, ExpiryConfidence)], existing_registry: &EventRegistry) -> Vec<CandidateMapping>`:
   - For each (key, instruments, confidence) triple:
     - Compute `earliest_expiry` as `instruments.iter().map(|i| i.expiry).min().unwrap()` -- used as the representative expiry date per research recommendation (most conservative).
     - Generate `event_id` as `"{ASSET}-{STRIKE}-{earliest_expiry}"` (same pattern as existing but using earliest expiry).
     - Check `existing_registry.lookup_by_event_id(&event_id)` -- skip if exists.
     - Check if any individual instrument is already mapped -- skip if so.
     - Build `CandidateVenues` extracting deribit (instrument_id), kalshi (instrument_id), and polymarket (condition_id + token_id). For Polymarket: instrument_id is the condition_id; for token_id, we need it from the DiscoveredInstrument. Since DiscoveredInstrument doesn't carry token_id, store condition_id for both and note that token_id resolution happens in the lifecycle manager where we have the raw market data. Use a placeholder approach: set polymarket to `Some((condition_id.clone(), String::new()))` -- the lifecycle wiring will supply the token_id from the PolymarketMarketInfo cache. **OR** (better): Add an optional `pub extra_id: Option<String>` field to DiscoveredInstrument to carry token_id for Polymarket instruments. Set it in `discover_polymarket_structured` (from Plan 01). If this changes Plan 01's struct, add the field here and update discover_polymarket_structured.
     - Set `expiry_confidence: *confidence`.
     - Push `CandidateMapping` to results.

**Important design note on Polymarket token_id:**
The `DiscoveredInstrument` struct currently has no field for Polymarket's token_id. Add `pub extra_venue_id: Option<String>` to `DiscoveredInstrument` (default None). In `discover_polymarket_structured` (from Plan 01), set this to the Yes-outcome token_id. In `filter_new_candidates_fuzzy`, when venue is Polymarket, use `(inst.instrument_id.clone(), inst.extra_venue_id.clone().unwrap_or_default())` for the polymarket tuple. Update the existing Deribit/Kalshi discovery to set `extra_venue_id: None`.

   - `filter_fuzzy_generates_correct_event_id`: Verify event_id uses earliest expiry.
