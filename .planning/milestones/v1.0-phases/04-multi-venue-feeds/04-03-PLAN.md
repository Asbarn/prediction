    **Health tracker** in `src/feed/health.rs`:
    - `VenueHealth` struct (thread-safe via `Arc<Mutex<>>` or `Arc` + atomics):
      - `venue: Venue`
      - `is_available: AtomicBool` (true = connected and streaming, false = disconnected)
      - `last_error: Mutex<Option<String>>` -- last error message
      - `last_message_at: Mutex<Option<chrono::DateTime<Utc>>>` -- timestamp of last received message
      - `connection_count: AtomicU64` -- number of connection attempts
    - Methods:
      - `new(venue: Venue) -> Arc<Self>`
      - `mark_available(&self)` -- set is_available=true, update last_message_at, emit `gauge!("feed_available", "venue" => venue).set(1.0)`
      - `mark_unavailable(&self, error: String)` -- set is_available=false, store error, emit `gauge!("feed_available", "venue" => venue).set(0.0)`
      - `is_available(&self) -> bool`
      - `record_message(&self)` -- update last_message_at to now
      - `increment_connections(&self)`
    - Purpose: Each venue supervisor calls mark_available/mark_unavailable. Health state is observable via metrics. In Phase 9, the /health endpoint reads this.

    **Module updates** in `src/feed/mod.rs`:
    - Add `pub mod polymarket;`
    - Add `pub mod kalshi;`
    - Add `pub mod health;`

    **Multi-venue pipeline** -- refactor `src/feed/pipeline.rs`:

    Keep `DataMode` enum but expand it: `Live`, `Replay { path, speed }`, `Mock` stays the same.

    Add `run_multi_venue_pipeline` function (the new primary entry point):
    ```
    pub async fn run_multi_venue_pipeline(
        mode: DataMode,
        config: &VenuesConfig,
        credentials: &Credentials,
        recording_dir: PathBuf,
        cancel: CancellationToken,
    ) -> anyhow::Result<mpsc::Receiver<MarketSnapshot>>
    ```

    Implementation:
    1. Create shared fan-in channel: `let (snapshot_tx, snapshot_rx) = mpsc::channel::<MarketSnapshot>(1024);`
    2. For Live mode:
       a. **Deribit pipeline** (existing):
          - Create `VenueRateLimiter` for Deribit
          - Create `RecordingService` for Deribit
          - Create `DeribitSupervisor` -> spawns task that produces `RawMessage`
          - Create `DeribitProcessor` with `snapshot_tx.clone()` as output
          - Spawn processor task
          - Each venue gets its own `cancel.child_token()` -- **CRITICAL for RELY-04: a venue crash must not propagate**
       b. **Polymarket pipeline** (new):
          - Create `RecordingService` for Polymarket (separate recording dir by venue)
          - Create `PolymarketSupervisor` -> spawns task producing `RawMessage`
          - Create `PolymarketProcessor` with `snapshot_tx.clone()` as output
          - Spawn processor task
          - Independent child CancellationToken
       c. **Kalshi pipeline** (new):
          - Load RSA private key from credentials (KALSHI_PRIVATE_KEY env var) or file path (config.kalshi.private_key_path)
          - If Kalshi credentials not provided, log a warning and skip Kalshi feed (graceful degradation from startup)
          - Create `RecordingService` for Kalshi
          - Create `KalshiSupervisor` with api_key_id and private_key -> spawns task
          - Create `KalshiProcessor` with `snapshot_tx.clone()` as output
          - Spawn processor task
          - Independent child CancellationToken
    3. `drop(snapshot_tx)` -- drop original sender so channel closes when all venue tasks complete
    4. Return `snapshot_rx`

    For Replay/Mock modes: keep the existing single-venue Deribit behavior (replay and mock are Deribit-specific in Phase 4).

    **IMPORTANT architectural notes:**
    - Each venue processor now takes an external `mpsc::Sender<MarketSnapshot>` for its output (the shared fan-in sender), instead of creating its own internal channel. Adjust the processor `new()` signatures from Plans 01/02 if needed -- the processor should accept the sender as a parameter rather than creating `(processor, receiver)`.
    - OR: each processor creates its own output channel and a small forwarding task pipes from processor's receiver into the shared fan-in sender. This is simpler (no API change) but adds one extra task per venue. Either approach works; prefer whichever keeps code cleaner.
    - **Pitfall 7:** Size the shared channel at 1024 (sufficient for 3 venues). Monitor via `try_send` + dropped message counter if concerned about backpressure.
    - **No shared mutable state between venues.** Each venue's book state is owned by its processor. Each venue's supervisor is independent.
