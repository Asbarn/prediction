    **4. Create `src/feed/traits.rs`:**
    Define three core traits:

    - `RawDataSource`: produces a stream/receiver of `RawMessage { text: String, received_at: DualTimestamp }`. This is the WS-level abstraction. Both DeribitClient and ReplayDataSource implement this.
    - `NormalizedDataSource`: produces a stream/receiver of `MarketSnapshot`. This is the snapshot-level abstraction for testing downstream consumers in isolation.
    - `Recorder`: accepts `RecordLine` items for recording. Takes venue + raw text + local timestamp + channel + optional instrument. This is the recording abstraction that Phase 4 venues reuse.

    Use `async_trait` pattern or `tokio::sync::mpsc::Receiver` rather than `impl Stream` return types to avoid RPITIT lifetime complexity. Prefer returning `mpsc::Receiver<RawMessage>` from a `start()` method, since the data source owns its background task.

    Define `RawMessage`:
    ```rust
    pub struct RawMessage {
        pub text: String,
        pub received_at: DualTimestamp,
    }
    ```

    **5. Create `src/feed/deribit/mod.rs`:**
    Declare submodules: `pub mod messages;`, `pub mod channels;`, `pub mod client;` (book and normalize added in Plan 02).

    **6. Create `src/feed/deribit/messages.rs`:**
    Implement ALL Deribit JSON-RPC serde structs as specified in the research. Key types:

    - `DeribitMessage` (untagged enum: `Response(RpcResponse)` | `Notification(RpcNotification)`)
    - `RpcResponse { jsonrpc, id, result: Value, error: Option<RpcError> }`
    - `RpcNotification { jsonrpc, method, params: NotificationParams { channel, data: Value } }`
    - `BookData { timestamp, instrument_name, change_id, prev_change_id: Option<i64>, update_type: Option<String>, bids: Vec<[f64; 2]>, asks: Vec<[f64; 2]> }`
      - Per research, the grouped `none.20.100ms` channel sends snapshots with `[[price, amount], ...]` arrays. Deserialize bids/asks as `Vec<[f64; 2]>` for the snapshot format. The `update_type` field distinguishes "snapshot" from "change" if Deribit sends both.
    - `TickerData` with ALL fields from the research (last_price, mark_price, index_price, greeks, funding, stats, etc.)
    - `TickerGreeks { delta, gamma, vega, theta, rho }`
    - `TickerStats { volume, volume_usd, high, low, price_change }`
    - `TradeData` (single trade) -- note: the trades channel sends `data` as a `Vec<TradeData>`, not a single object
    - `PriceIndexData { timestamp, price, index_name }`

    All f64 fields are intentional at the serde boundary -- conversion to `rust_decimal::Decimal` happens in the normalization layer (Plan 02), NOT here. This avoids the precision pitfall documented in research by keeping the deserialization layer simple and handling Decimal conversion with explicit rounding in normalize.rs.

    Add `#[cfg(test)] mod tests` with unit tests that deserialize sample JSON strings for each message type. Include at least one test per channel type using realistic Deribit JSON from the research examples.

    - Implement `ChannelKind::parse(channel: &str) -> ChannelKind` that parses a channel name string (e.g., "book.BTC-27JUN25-100000-C.none.20.100ms") and returns the kind
    - Implement `build_subscription_channels(instruments: &[String]) -> Vec<String>` that takes an instrument list and produces the full set of channel names for subscription: `book.{inst}.none.20.100ms`, `ticker.{inst}.raw`, `trades.{inst}.raw` for each instrument, plus `deribit_price_index.btc_usd`
    - Extract instrument name from channel string where applicable (e.g., from "ticker.BTC-27JUN25-100000-C.raw" extract "BTC-27JUN25-100000-C")

    Add unit tests for channel parsing and construction.

  <action>
    **1. Create `src/feed/deribit/client.rs`:**
    Implement `DeribitClient` struct that:

    - Takes `DeribitConfig` (ws_url, etc.), a list of instrument names (`Vec<String>`), and a `CancellationToken`
    - Has a `start()` method that returns `mpsc::Receiver<RawMessage>` (buffer size 1024 per research recommendation)
    - `start()` spawns a tokio task that:
      1. Connects to `config.ws_url` via `tokio_tungstenite::connect_async()`
      2. Splits the stream into read/write halves using `futures_util::StreamExt` and `SinkExt`
      3. Builds the subscription channel list using `channels::build_subscription_channels()`
      4. Sends a JSON-RPC 2.0 `public/subscribe` request with all channels in a single batch (avoiding per-channel rate limit issues per research)
      5. Uses an `AtomicU64` counter for JSON-RPC request IDs
      6. Enters a read loop that:
         - Reads each `Message::Text` frame from the WebSocket
         - Creates a `RawMessage` with `DualTimestamp::now()` for the receive timestamp
         - Sends the raw message through the `mpsc::Sender`
         - Handles `Message::Close` by logging and breaking
         - Ignores `Message::Ping`/`Message::Pong` (tokio-tungstenite handles pong automatically, but we must keep reading per research pitfall 2)
         - Respects `CancellationToken` via `tokio::select!`
      7. On connection error, logs the error and exits (NO reconnection in Phase 2 -- that is Phase 3)

    - Implement the `RawDataSource` trait for `DeribitClient` (the `start` method returns the receiver)

    **2. Optionally add `instruments` field to `DeribitConfig` in `src/config/venues.rs`:**
    Add `instruments: Vec<String>` to `DeribitConfig` so the instrument list comes from `venues.toml`. This is per the locked decision: "Instrument list is dynamic -- comes from config in Phase 2". Update `config/venues.toml` with a sample instrument list:
    ```toml
    [deribit]
    ws_url = "wss://test.deribit.com/ws/api/v2"  # Use testnet for dev
    rate_limit_per_second = 20
    heartbeat_interval_ms = 10000
    instruments = ["BTC-27JUN25-100000-C"]
    ```

    **Note:** Log the subscribe response (success or error). If the response contains an error, log it at error level. Do not crash on subscribe error in Phase 2 -- Phase 3 adds retry logic.

    **Connection error handling:** If `connect_async` fails, return an error from `start()`. The caller decides whether to retry (Phase 3) or fail.
