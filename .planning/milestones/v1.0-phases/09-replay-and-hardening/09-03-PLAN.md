  <action>
    **Supervisor changes (all three follow the same pattern):**

    1. **DeribitSupervisor** (`src/feed/deribit/supervisor.rs`):
       - Add `use std::sync::Arc;` and `use crate::feed::health::VenueHealth;` imports
       - Add `health: Arc<VenueHealth>` field to the `DeribitSupervisor` struct
       - Add `health: Arc<VenueHealth>` parameter to `DeribitSupervisor::new()` and store it
       - In `run()`, at the top of the reconnection loop (after `attempt += 1`), call `self.health.increment_connections();`
       - In `run()`, where `received_first` is set to true (the first-message block inside `Ok(mut raw_rx)` arm), call `self.health.mark_available();` right after `backoff.reset();`
       - In `run()`, where connection is lost (the `None =>` branch of `msg = raw_rx.recv()`), call `self.health.mark_unavailable("connection lost".to_string());`
       - In `run()`, where connection attempt fails (the `Err(e)` branch of `client.start().await`), call `self.health.mark_unavailable(format!("connection failed: {e}"));`

    2. **PolymarketSupervisor** (`src/feed/polymarket/supervisor.rs`):
       - Same pattern as DeribitSupervisor: add `health: Arc<VenueHealth>` field
       - Update `new()` to accept `health: Arc<VenueHealth>` parameter
       - Add `health.increment_connections()` at each attempt
       - Add `health.mark_available()` on first message received
       - Add `health.mark_unavailable(...)` on connection lost and connection failed

    3. **KalshiSupervisor** (`src/feed/kalshi/supervisor.rs`):
       - Same pattern: add `health: Arc<VenueHealth>` field
       - Update `new()` to accept `health: Arc<VenueHealth>` parameter
       - Add health lifecycle calls in the same locations

    **Pipeline changes** (`src/feed/pipeline.rs`):

    4. Update `forward_snapshots()` to accept an `Option<Arc<VenueHealth>>` parameter:
       - Add `health: Option<Arc<VenueHealth>>` parameter after `venue: Venue`
       - In the `Some(snap) =>` branch (successful snapshot forwarded), call `if let Some(h) = &health { h.record_message(); }` before sending to fan_in_tx
       - This provides continuous last_message_at updates as long as data is flowing

    5. In `run_live_multi_venue()`, pass the `Arc<VenueHealth>` clone to each supervisor's `new()`:
       - Deribit section: pass `health.clone()` as the last parameter to `DeribitSupervisor::new(..., health.clone())`
       - Polymarket section: pass `health.clone()` to `PolymarketSupervisor::new(..., health.clone())`
       - Kalshi section: pass `health.clone()` to `KalshiSupervisor::new(..., health.clone())`

    6. In `run_live_multi_venue()`, pass `Some(health.clone())` to each `forward_snapshots()` call:
       - Update all three `tokio::spawn(forward_snapshots(...))` calls to include the health parameter

    7. In `run_pipeline()` (Mock/Replay single-venue), the `forward_snapshots` function is not called, so no changes needed there.

    **Important:** The `health` variable in each venue section block is already `Arc<VenueHealth>` from `VenueHealth::new()`. We clone it to pass both to the supervisor and to forward_snapshots. This is cheap (Arc clone is just a refcount increment).
