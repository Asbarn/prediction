1. **Create `src/replay/mod.rs`** with multi-venue replay orchestration:

   a. `ReplayCorpus` struct:
      - `entries: Vec<RecordLine>` -- all venues merged, sorted by `local_ts`
      - `async fn load_directory(recordings_dir: &Path) -> anyhow::Result<Self>`:
        - Iterate through subdirectories: "deribit", "polymarket", "kalshi"
        - If a venue directory doesn't exist, log warning and skip (graceful degradation per RELY-04 pattern)
        - For each existing venue directory, read all `.jsonl` files (sorted by filename for chronological order)
        - Parse each line as `RecordLine`, skip unparseable lines with warning
        - Sort all entries by `local_ts` across all venues
        - Log summary: total entries per venue, time range
      - `fn venues(&self) -> HashSet<Venue>` -- returns which venues have data

   b. `pub async fn run_replay_pipeline(...)` function:
      - Parameters: `recordings_dir: PathBuf`, `config: &VenuesConfig`, `speed: f64`, `cancel: CancellationToken`
      - Returns: `anyhow::Result<PipelineHandles>` (with empty venue_health vec since replay doesn't have live connections)
      - Load ReplayCorpus from `recordings_dir`
      - Group entries by venue: `HashMap<Venue, Vec<RecordLine>>`
      - Create shared fan-in channel `(snapshot_tx, snapshot_rx)` with FAN_IN_BUFFER=1024
      - For each venue with data:
        - Write entries to a temporary JSONL file (so existing ReplayDataSource can read them)
        - Create ReplayDataSource for that temp file at the given speed
        - Start the appropriate per-venue processor (DeribitProcessor for Deribit, PolymarketProcessor for Polymarket, KalshiProcessor for Kalshi)
        - Spawn forwarding task piping venue snapshots to shared fan-in
      - Return PipelineHandles with snapshot_rx and empty venue_health

   c. **ALTERNATIVE (simpler approach)**: Instead of temp files, extend ReplayDataSource to accept `Vec<RecordLine>` directly:
      - Add a constructor: `ReplayDataSource::from_records(records: Vec<RecordLine>, speed: f64, cancel: CancellationToken) -> Self`
      - This avoids temp file overhead and is cleaner
      - The existing `start()` implementation loop is almost identical -- factor the common loop into a shared helper

2. **Extend `ReplayDataSource` in `src/feed/mock/replay.rs`**:
   - Add `ReplayDataSource::from_records(records: Vec<RecordLine>, speed: f64, cancel: CancellationToken)` constructor
   - Use an enum internally: `ReplaySource { File(PathBuf), Records(Vec<RecordLine>) }`
   - In `start()`, if source is Records, use them directly instead of reading from file
   - **Fix DualTimestamp in replay**: Construct `DualTimestamp` using the recorded `local_ts` from RecordLine instead of `DualTimestamp::now()`. Use `DualTimestamp::from_wall(record.local_ts)` if that method exists, or create RawMessage with a DualTimestamp where `wall = record.local_ts` and `mono = Instant::now()` (mono is only for in-process elapsed timing and has no meaningful replay value per research pitfall #2)
   - Add test: `replay_from_records_produces_messages`

3. **Add replay_mode staleness bypass to `SpreadEngine` in `src/spread/engine.rs`**:

   - Add `pub fn with_replay_mode(mut self, replay: bool) -> Self` builder method
   - In the staleness check within `run()` (or wherever `Utc::now()` is compared against exchange timestamps), skip the wall-clock staleness comparison when `self.replay_mode` is true
   - The processor-level `is_stale` flag on MarketSnapshot (based on sequence gaps) still works correctly in replay, so only skip the time-based checks
   - Research recommends approach 1: disable staleness gates entirely in replay mode (simplest, recommended for v1)
