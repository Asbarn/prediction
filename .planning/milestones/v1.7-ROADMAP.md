# Roadmap: v1.7 Prediction Market Signal Pipeline

## Overview

Get Polymarket data flowing from production EC2 and generate cross-asset arbitrage signals (options-implied probability vs prediction market price). Four phases: diagnose and harden the Polymarket WebSocket connection, generalize the signal engine to work with any options/prediction venue combination, add REST polling as a fallback data source, and verify end-to-end signal generation in production.

## Phases

**Phase Numbering:**
- Integer phases (40, 41, 42, 43): Planned milestone work
- Decimal phases (e.g., 41.1): Urgent insertions (marked with INSERTED)

- [ ] **Phase 40: Polymarket WebSocket Diagnosis and Data Watchdog** - Investigate WS failure from EC2, implement data inactivity detection and forced reconnection
- [ ] **Phase 41: Signal Engine Generalization** - Remove hardcoded venue references so CrossAssetEngine works with any options+prediction market pair
- [ ] **Phase 42: REST Polling Fallback and Source Coordination** - Add REST-based price polling when WebSocket is unavailable, with exclusive-mode switching
- [ ] **Phase 43: End-to-End Production Verification** - Prove signal pipeline generates real arbitrage signals on AWS EC2

## Phase Details

### Phase 40: Polymarket WebSocket Diagnosis and Data Watchdog
**Goal**: Polymarket data flows reliably from production EC2, with automatic recovery from silent freezes
**Depends on**: Nothing (first phase of v1.7)
**Requirements**: POLY-01, POLY-02, POLY-03
**Success Criteria** (what must be TRUE):
  1. Operator can see a documented diagnosis of the Polymarket WebSocket failure mode from EC2 (connection reset, silent freeze, geo-block, or working)
  2. Polymarket supervisor automatically detects data inactivity (no order book updates) and triggers reconnection after configurable timeout
  3. Polymarket WebSocket feed delivers order book data from the production EC2 instance (or diagnosis conclusively shows it cannot)
  4. Prometheus metrics reflect Polymarket feed liveness state and reconnection events
**Plans**: 2 plans

Plans:
- [ ] 40-01-PLAN.md — Config extension (data_timeout_secs) and WS diagnostic integration test
- [ ] 40-02-PLAN.md — Supervisor data inactivity watchdog with tokio::time::timeout

### Phase 41: Signal Engine Generalization
**Goal**: CrossAssetEngine correctly generates arbitrage signals using options-implied probabilities from any venue (Deribit or Derive) paired with any single prediction market
**Depends on**: Nothing (independent of Phase 40)
**Requirements**: SIG-01, SIG-02, SIG-03
**Success Criteria** (what must be TRUE):
  1. ImpliedProbability values carry their source venue (Deribit or Derive), not a hardcoded assumption
  2. CrossAssetEngine generates ArbSignals when only one prediction market venue has data (Polymarket alone, without Kalshi)
  3. CrossAssetEngine pairs Derive-sourced implied probabilities with prediction market snapshots to produce correctly attributed signals

### Phase 42: REST Polling Fallback and Source Coordination
**Goal**: Polymarket price data is available via REST polling when WebSocket is unreliable, with clean exclusive-mode switching between sources
**Depends on**: Phase 40 (diagnosis determines whether REST is fallback or primary), Phase 41 (data model in place for REST-sourced snapshots)
**Requirements**: POLY-04, POLY-05
**Success Criteria** (what must be TRUE):
  1. REST poller fetches current Polymarket prices using existing reqwest/governor infrastructure and produces MarketSnapshot messages
  2. System runs exactly one data source at a time per venue -- WebSocket or REST, never both simultaneously
  3. Source coordinator automatically switches to REST on WebSocket data silence and back to WebSocket after sustained reconnection
  4. Prometheus metrics show current data source mode (WS vs REST) and REST poll success/failure counts

### Phase 43: End-to-End Production Verification
**Goal**: The complete signal pipeline is verified working on production EC2 with real market data producing real arbitrage signals
**Depends on**: Phase 40, Phase 41, Phase 42
**Requirements**: VER-01, VER-02
**Success Criteria** (what must be TRUE):

  2. Signal JSONL logs contain ArbSignal entries with correct venue attribution (options venue + prediction market venue)
  3. Spread JSONL logs contain entries from live Polymarket data (via WS or REST) paired with options-implied probabilities
